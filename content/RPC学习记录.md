# RPC 学习记录

> 2026-10 学习 · 从 Socket 底层到 Thrift 框架，再到 RPC 与负载均衡的辨析。

## 一、底层基础：Socket & FD

- **FD（文件描述符）**：Linux「一切皆文件」，fd 是内核分配给打开资源的整型编号；文件、管道、socket、终端都占 fd。Socket 一定占用 fd，但 fd 不一定是 socket。
- **TCP Socket 核心系统调用**：
  - `socket()`：创建套接字，返回 fd
  - `bind(ip+port)`：绑定端口，告知内核该端口数据包交给此 socket
  - `listen(backlog)`：开启监听，标记被动接待；内核完成三次握手，新连接入等待队列，不阻塞进程
  - `accept()`：阻塞等待连接，取出连接，返回**新通信 socket 的 fd**
- **两类 socket 分工**：监听 socket（仅收新连接，全局唯一）vs 通信 socket（每客户端连接 1 个，close 后 fd 释放）
- **资源上限**：单进程 fd 上限 `ulimit -n`（默认 1024，超出报 `too many open files`）；整机 `file-max`；一个端口同一时间只能被一个进程 bind，但可承载大量并发连接
- **长短连接**：短连接请求完即关闭、fd 快速复用；长连接持续持有 fd，需调大 fd 阈值

## 二、HTTP 接口完整流程 & 三种「服务注册」

### HTTP 调用全链路

客户端构造 HTTP 报文 → TCP 传输 → 服务端端口监听 → Web 框架路由匹配 → 执行业务代码 → 组装响应报文原路返回。HTTP 是文本型应用层协议，跑在 TCP 之上。

### 三种不同含义的「注册」

| 类型 | 层面 | 作用 | 生命周期 |
|---|---|---|---|
| 路由注册 | 框架内存 | 维护 `请求方法+路径 → 业务函数` 映射（Gin：`r.POST("/api/register", handler)`） | 程序退出即消失 |
| 系统服务注册 | OS（systemd/Windows 服务） | 后台常驻、开机自启、崩溃重启；只管理进程，不处理网络 | 随系统 |
| 微服务注册 | 注册中心（Nacos/Eureka） | 服务上报 `IP+端口+服务名`，供服务发现 | 随服务在线状态 |

### HTTP 常见错误含义

- 404：路由路径不存在
- 405：路径匹配，但请求方法不匹配
- 500：路由找到，业务代码异常
- 连接超时：网络不通 / 服务未启动 / 端口未监听

## 三、RPC 框架（Thrift）作用与全流程

> 本质：在原生 Socket TCP 底座之上封装的上层库，不替代 socket，底层依旧调用 socket/bind/listen/accept。

- **裸写 Socket 痛点**：手动处理字节流、粘包分包、序列化、路由、超时、连接异常，易出内存/fd 泄漏。
- **Thrift 核心模块**：
  - IDL：定义服务、方法、参数；自动生成客户端与服务端骨架
  - Protocol：二进制序列化/反序列化（TBinary / TCompact），比 JSON 更小更快
  - Transport：封装 socket，`TServerSocket` 底层就是 socket 系统调用
  - Server：单线程 / 多线程 / IO 多路复用（epoll）处理连接分发
- **路由规则**：匹配 `服务名 + 方法名`，而非 HTTP 的 URL 路径
- **时序简述**：客户端调用 → IDL 序列化二进制 → socket 发送 → 服务端 accept 拿 conn fd → recv 读字节 → 反序列化得方法+参数 → 路由执行业务 → 序列化回传 → 客户端反序列化 → 短连接 close 释放 fd

## 四、框架使用场景

| 场景 | 做法 | 例子 |
|---|---|---|
| 业务开发（Web/微服务） | 几乎全用框架，快速开发 | Gin/SpringBoot（HTTP）、Thrift/gRPC（RPC） |
| 底层基础设施 | 裸写/轻量网络库，追求极致性能 | Nginx、Redis、MySQL（socket/libuv/libevent 手写） |
| 轻量网络库 | 仅封装 IO 多路复用，无 IDL/序列化/路由 | asio / libuv / libevent |

## 五、RPC 与负载均衡概念辨析

- **RPC 不是调度系统**：核心是远程过程调用（IDL、序列化、网络传输、方法路由），底层基于 Socket/TCP；原生 Thrift/gRPC 不带负载均衡、服务发现。Dubbo 是在 RPC 之上叠加服务治理（注册发现、负载均衡、熔断）。
- **类比**：RPC 是长途电话；服务治理/负载均衡是调度中心。电话本身不负责调度。
- **两类负载均衡**：
  - 客户端 LB（微服务 RPC）：客户端从注册中心拉实例列表，本地算法选节点直连
  - 服务端 LB（Nginx/网关）：请求先到网关再转发，HTTP 常用
- **概念区分**：RPC=远程调用通信能力；注册发现=维护可用实例地址；负载均衡=流量分发策略；熔断降级=异常保护机制

### 完整微服务调用链路（注册发现 + LB）

1. 服务实例启动，将 `IP+端口` 注册到注册中心（Nacos/Eureka）
2. 客户端拉取实例列表
3. 负载均衡算法挑选目标实例
4. RPC 客户端建立 Socket 连接，发起远程方法调用
5. 服务端处理请求并返回结果

## 六、关键结论

1. 无论 HTTP 框架还是 Thrift RPC 框架，底层最终依赖操作系统 Socket、TCP 协议栈、fd 资源；fd、端口限制对它们全部生效。
2. HTTP 用文本 JSON，适合对外网关/浏览器；Thrift/gRPC 二进制 RPC 多用于内网微服务，性能更好。
