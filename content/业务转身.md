### 3.1 整体组网拓扑

1. **内置代理组网** `OP(PM+Agent) ↔ HCS/存储`
2. **外置代理组网（VHA）** `OP‑PM ↔ 网络 ↔ 外置Agent ↔ HCS/存储`

- 管理网：OP‑PM 与 Agent 之间注册、指令下发。
- 备份网：Agent 与 HCS 之间做备份数据流。

> 关键点：OP 只跟 Agent 通信；Agent 才跟 HCS 存储通信。

### 3.2 部署与注册流程简述

1. 硬件：网卡规划 4 张网卡，Bond/Eth‑Trunk，LACP/M‑LAG，交换机堆叠。
2. 五大网段隔离；配置 zone 白名单。
3. NTP 时间同步 (UDP123)；导入 License；版本校验；SSH/NFS/SFTP 可用。
4. 客户端主机安装 Agent + AppPlugin_VAS 插件。
5. 配置域名映射 (hosts/DNS)，在 OP 侧执行注册。

### 3.3 注册失败标准排查步骤（新人排障模板）

1. 判断故障大类：代码问题 / 底层网络（VPN、路由、网卡、DNS、防火墙）
2. 分层连通校验
    - OP‑PM ping Agent（管理网）
    - Agent ping HCS（业务网）
    - Agent ping HCS（备份网）
3. 判断代理类型
    - 外置：检查 OP 本机 hosts，curl 验证域名解析
    - 内置：检查 Agent 侧域名映射
4. 分别查看：OP‑PM 调度日志、agent‑log，定位真实报错。

### 3.4 日志位置

1. OP 端 Nginx 日志：仅看 ping 连通，不能定位业务报错。
2. agent‑log：注册、建链、任务执行真实报错。
3. OP 内部：PM 模块做任务下发；Kafka 作为内部消息队列。
4. 内置 Agent 业务日志：OP 机器；外置 Agent 业务日志：外置主机。

### 3.5 核心业务流程（业务链路）

#### 流程 1：Agent 插件启动流程

`PluginMain入口` → 解析参数、初始化环境 → 创建引擎 → 注册扫描 / 快照 / 备份处理器 → Thrift 长连接监听等待 OP‑PM 任务下发 → 根据任务类型进入扫描 / 快照 / 备份分支。

#### 流程 2：VDC 资源扫描（上报 ECS、磁盘给 OP）

入口：`listApplicationResourceV2`

1. 环境初始化，刷新 Token
2. 获取租户、O‑VDC/I‑VDC 列表
3. 循环遍历每个 VDC，设置上下文
4. callApi 调用 HCS 接口，多线程采集 ECS、磁盘、规格
5. 序列化整理资源，上报 OP 后台

> 支持全量扫描、多轮扫描策略。

#### 流程 3：快照创建流程（备份前置动作）

入口：`DoCreateSnapshot`，传入卷列表

1. 卷互斥锁，防止同卷并发快照
2. 跳过共享卷，组装请求
3. `CreateSnapshot`调用存储接口创建快照
4. `ConfirmSnapshotReady`轮询阻塞等待快照就绪。

#### 流程 4：全量备份主流程

OP 下发任务 → Agent 执行业务

1. PRE‑INIT：初始化任务上下文、JobInfo、ConnInfo、各类 handler，分配内存（元数据、源端、备份载荷）
2. PRE‑Hook：前置校验，检查 ECS、磁盘、快照状态
3. 获取卷信息`GetVolumeHandler`，区分集中式 / 分布式存储分支
4. 创建任务，异步分发子任务`AsyncExecuteBackupSubJob`
5. 子任务：IAM 鉴权 → 创建快照 → LUN 映射 → iSCSI 挂载快照卷 → bitmap 拷贝有效块
6. 后置：卸载 LUN，清理临时快照，释放资源，任务上报。

#### 流程 5：备份任务状态机完整阶段

1. **PRE‑前置阶段**：任务初始化、hook、备份前置检查、创建快照、激活快照、采集整机 & 卷元数据、保存元数据。元数据保存在 OP，用于增量链、恢复、校验。
2. **GENERATE‑子任务生成**：加载快照信息、加载 VM 元数据、按卷拆分生成子任务。
3. **EXEC‑执行阶段**：子任务初始化、上报进度、获取脏块、拷贝脏块。
4. **POST‑JOB 收尾清理**：更新快照元信息、清理残留快照、写 checkpoint 标记、执行钩子。

> 快照清理逻辑
> 
> - 全量备份：清理全部历史快照链。
> - 增量备份：只删除上一次快照，维持增量链。
> - 关键文件：[snapshot.info](https://snapshot.info)‑本次、[snapshot.info](https://snapshot.info)‑上次、snapshot‑tobeDeleted 待删除列表。

### 3.6 VHA 双活备份改造业务逻辑

改造目标：HCS VHA 双活虚拟机能够正常备份，识别主 / 容端，获取 LUN，做快照，区分全量 / 增量。

1. **Step1 VHA 实例识别** 输入 VM‑ID/VM‑Name；调用`GetVhaInstanceInfo()、IsVhaVolume()`；拿到实例信息，区分主端 / 容端。风险点：VHA 接口 Endpoint、IAM‑Token 正确性。
2. **Step2 ID 转换链路 VM →卷 → LUN**`VM‑ID → GetMachineMetaData → ShowVolumeDetail(卷ID) → GetVolumeLun → GetVolumeHandler拿到LUN`

> 没有 LUN，无法下发快照，备份中断。

3. **Step3 快照逻辑**

- 判断快照是否存在；存在走增量，不存在新建快照走全量。
- VHA 快照 ID 命名：`SNAP‑lunId‑time`。
- 通过 LUN 调用存储接口创建快照；失败必须回滚删除快照，不遗留脏快照。

4. **代码分支改造点**

- 优先判断 VM 是否 VHA 实例；是则走 OceanStor 快照链路；普通 VM 走原有 cinder 链路。
- `GetSnapShotByID`由 VM 维度改为 LUN 维度查询。
- 重写`checkBackupJobType`适配 VHA 全量 / 增量判断。
- 增加 CG 一致性组判断、主机 / 存储故障异常分支。

5. **必须覆盖的测试 case**

- 上一次备份失败，本次增量是否自动转全量。
- 普通非 VHA 虚拟机备份兼容性。
- VM 重名、VHA 实例名重复场景。
- 主活容挂、主挂容活、两端都存活场景。
- 快照丢失、网络超时、SSL 异常、DNS 异常。
